# M1.5: deterministic, defined-behavior C fuzzing

Mini-C's independent reference corpus is generated by `mini-c-fuzz`. The generator is a Rust crate with no dependency on the Mini-C semantic checker or backend. It builds a reproducible sequence of arithmetic instructions and computes the expected value with checked Rust integer operations; C source is separately rendered and then parsed by `mini-c-syntax`.

## Running it

```sh
cargo test -p mini-c-fuzz
cargo build -p mini-c-fuzz
cargo run -q -p mini-c-fuzz -- 42 120 > case.c
python3 tools/fuzz_reference.py --seed-start 0 --seed-count 12 --steps 120
python3 tools/fuzz_reference.py --seed-start 100 --seed-count 64 --steps 300
```

The CLI arguments are `[seed] [steps]`, with at most 10,000 steps. Seed and step count reproduce **the exact same source** for the same generator revision. The generated `main` returns **1 for success**, not 0: it checks that its computed final value equals the oracle's expected value. Reference runners must explicitly accept exit code 1; exit code 0 is an oracle mismatch, not a pass.

The Python runner needs Python 3.10+, Rust-built `target/debug/mini-c-fuzz`, GCC and Clang. It compiles each case with GCC and Clang at `-std=c11 -O0` and `-O2`; with sanitizers enabled it also tests GCC UBSan and Clang ASan+UBSan. To disable sanitizer variants for a quick local run, pass `--skip-sanitizers`. Compilation and execution each have an adjustable timeout (`--timeout`, in seconds). Sanitizer subprocesses use dedicated non-1 failure exit codes, and their diagnostic output is checked as well: a sanitizer error must **never** be mistaken for the generated program's normal exit code 1.

On any compilation, sanitizer, execution, generation or oracle mismatch, the runner stops and retains `target/fuzz-artifacts/seed-NNNNNN/` including `case.c`, `results.json`, invoked commands, outputs, compiler versions, revision and seed. Passing cases are cleaned up to avoid retaining many executables. Reproduce a seed using the command in `results.json`.

## Defined-behavior invariants

- Values remain in **[-32767, 32767]**, a range representable by C's signed `int` on all conforming implementations.
- All variables are initialized before use: `x` starts at 1; the loop-local `remaining` starts at 1, 2, 3 or 4.
- Add, subtract and multiply operations are emitted only if checked Rust arithmetic succeeds **and** stays in the portable range. Signed division/remainder use positive nonzero constants, ruling out zero divisors and `INT_MIN / -1`.
- The conditional `if (x >= 0) x = x - 1; else x = x + 1;` always moves one unit toward zero (or from zero to -1), so cannot overflow or leave the allowed range. The trace records only its executed operation.
- The bounded loop `while (remaining > 0)` divides `x` by 2 and decrements `remaining` each iteration; it executes exactly 1–4 times. The trace contains one division per executed iteration.
- No pointers, array indexing, uninitialized reads, shifts, aliasing, unsequenced conflicting accesses, unspecified evaluation-order dependencies, recursion or unbounded loops are generated.
- No reliance on signed overflow, `-fwrapv`, implementation-defined signed conversions or external input; generated programs are deterministic.

The oracle is independent of the Mini-C AST, typing and backend. The tests also replay the numeric instruction trace, asserting the expected value and range after **every** operation. GCC and Clang provide additional independent execution oracles; they should be checked at multiple optimization levels, with runtime sanitizers.

## Continuous integration

The targeted `syntax.yml` workflow tests the fuzzer crate, then runs a short reference corpus with both compilers and sanitizers. The separate `fuzz.yml` workflow runs 64 longer cases weekly and on manual dispatch. Each workflow uploads the retained failure directories as GitHub Actions artifacts on failure; passing cases leave no large binaries.

For triage, preserve the Git commit, seed, steps, generated C, compiler version and flags. Add a failing seed to the fixed smoke corpus after the underlying issue is understood. This is an early integer-C corpus, **not a general-purpose C fuzzer**. Future phases may add pointer or array operations only with explicit defined-behavior rules and an independent reference model.
